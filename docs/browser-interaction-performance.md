# 浏览器交互性能修复

日期：2026-10-31。基线为 `2d11abe`，修复版本为 0.3.2。

## 原因和改动

- 手动滚动原先仍走空闲帧限速：每帧确认额外等待约 41.7ms，与捕获、编码和传输时间叠加，复现页只有约 15fps。鼠标、滚轮、键盘和样式拖动现在会开启短暂交互窗口，立即确认帧；结束后恢复空闲节奏。
- 120Hz 触控板输入原先逐条串行执行，5 秒滚动之后仍积压约 5 秒。现在合并同一标签、位置、方向和修饰键下尚未执行的滚轮增量，保留总距离。点击、其它命令、方向变化或坐标变化构成合并边界，过期标签输入仍拒绝执行。
- 每个输入包原先会查询 frame 树，即使页面已经处于人工控制状态。现在复用已知状态，仅在需要从 Agent 交还控制权时遍历；新文档的默认来源仍为 human。
- 启动参数原先强制关闭 GPU，宽页面的高分辨率捕获受到软件渲染限制。移除该覆盖，使用 Chromium 的默认加速与回退策略；画面流允许最多三帧在途。空闲 ACK 按时间分散，避免扩大在途数量后增加空闲帧率。

保留 Retina DPR 2、JPEG quality 88、2048px 最大边长和原有页面/图片坐标映射。没有改写选区高亮、网站 CSS 或浏览器工具授权边界。

## 本机实测

同一个 Electron → IPC → BrowserOS → 图片解码链路，自动产生约 120Hz 连续滚动；每段 5 秒。分别测量未选中和选中固定页头后的状态。最终版本在两种页面各跑三轮；宽页面包含 120 个条目。

| 场景                 | 未选中 fps | 已选中 fps | 帧间隔 P95（ms） | 停手后输入完成（ms） |
| -------------------- | ---------: | ---------: | ---------------: | -------------------: |
| 修复前，自适应页面   |  15.2–15.2 |  14.6–14.6 |        75.4–76.6 |        5152.0–5482.0 |
| 0.3.2，自适应页面    |  58.6–59.1 |  58.9–59.2 |        18.9–19.6 |            42.0–46.0 |
| 0.3.2，1100px 宽页面 |  56.3–56.6 |  55.5–56.7 |        28.2–32.9 |            41.0–72.0 |

打包后的 0.3.2 另测了宽页面中的普通文档流选区（选中元素会随滚动离开视口）：未选中 48.1fps、已选中 55.8fps，帧间隔 P95 为 30.4/32.2ms，停手后输入完成为 54/59ms。

`presentedFps` 统计嵌入图片已完成 decode、仍对应当前图片且内容变化的帧；不是外层 React 页面或原生网页的 requestAnimationFrame 频率。输入完成时间包含队列屏障与后续两次原生渲染帧。基线在修复前隔离构建中测量，旧队列的排空按实际滚动位置确认。不同网页内容、屏幕和机器负载会影响数值。

## 验证方法

```sh
npm run build
npx tsx --test tests/browser-input-queue.test.ts
ATHENA_PERF_ROUNDS=3 npx tsx tests/browser-scroll-performance.e2e.ts
ATHENA_PERF_WIDE=1 ATHENA_PERF_ITEMS=120 ATHENA_PERF_ROUNDS=3 npx tsx tests/browser-scroll-performance.e2e.ts
```

性能用例断言滚动帧率、帧间隔、输入排空时间和滚动距离。队列用例覆盖连续增量、点击边界、反向/横向/修饰键变化、失效标签、无效数据、来源切换及空闲 ACK 释放。

另运行真实 BrowserOS 的浏览器套件、页面缩放、选区反馈、编辑器布局和延迟解码旧帧隔离用例。首次全量运行中跨域 iframe 用例曾偶发失败；原版及修复版单独运行通过，修复版定向连续 10 次通过。随后完整浏览器回归 26 项全部通过，单元套件 123 项通过、11 项按环境跳过；缩放、选区、布局和延迟解码用例全部通过。此现象没有被当作滚动根因，也没有据此加入固定延时或绕过命中检查。

本次未改动运行中的既有用户配置与网页。修复包单独生成，源码推送和发布属于后续操作。
